<task type="auto">
  <name>Task 1: Create aide-verify.sh verification script</name>
  <files>scripts/aide-verify.sh</files>
  <action>
Create `scripts/aide-verify.sh` — a bash script that runs three stages in fixed order, failing fast on first failure:

1. **BUILD stage**: Run `make build`. On success print `[BUILD] PASS`, on failure print error output then `[BUILD] FAIL` and exit 1.

2. **FORMAT stage**: Run `make code-format` (applies clang-format in-place), then `git diff --exit-code -- src/main src/test` to detect if any files changed. If diff is non-empty, print the diff (for agent diagnosis) then `[FORMAT] FAIL` and exit 1. If clean, print `[FORMAT] PASS`.

3. **TEST stage**: Run `make run-tests`. On success print `[TEST] PASS`, on failure print `[TEST] FAIL` and exit 1.

Script requirements:
- `#!/bin/bash` with `set -uo pipefail` (not `set -e` — handle exit codes manually per stage)
- Each stage captures output inline (not suppressed) so agents see compiler errors, test failures, etc. before the tagged line
- Tagged lines (`[BUILD] PASS`, `[FORMAT] FAIL`, etc.) are the LAST line printed for each stage — enables `grep '\[BUILD\]'` to get the definitive result
- Non-zero exit on any failure
- No partial-run flags — always runs all three stages up to first failure
- Add a brief header comment explaining what the script does and that FORMAT FAIL leaves formatted files in the working tree (agent should commit the formatting fix)
- Make the script executable: `chmod +x scripts/aide-verify.sh`

Do NOT modify GNUmakefile, run-tests-wine.sh, or any existing scripts. This script wraps existing make targets.
  </action>
  <verify>
    <automated>bash -n scripts/aide-verify.sh && test -x scripts/aide-verify.sh && head -5 scripts/aide-verify.sh | grep -q '#!/bin/bash' && grep -q '\[BUILD\]' scripts/aide-verify.sh && grep -q '\[FORMAT\]' scripts/aide-verify.sh && grep -q '\[TEST\]' scripts/aide-verify.sh && echo "PASS"</automated>
  </verify>
  <done>scripts/aide-verify.sh exists, is executable, passes bash syntax check, contains all three tagged output markers ([BUILD], [FORMAT], [TEST]), and uses git diff --exit-code for format checking.</done>

**Dockerfile.build changes:**

Add Wine packages to the existing `apt-get install` line. Wine on Debian 11 requires enabling i386 architecture for 32-bit test executables. Insert BEFORE the existing `RUN apt-get update` line:

```
RUN dpkg --add-architecture i386
```

Then add `wine wine32` to the existing `apt-get install` package list (keep existing packages, just append). Do NOT change the ENTRYPOINT — tests run as a separate CI step, not as part of the default build.

**build-master.yaml changes:**

Add a "Run tests (Wine)" step between the existing "Build" step and the "Prepare artifact package" step. This step runs inside the same Docker container that built the project. Since `make build-docker` mounts the repo as `/bemanitools` and build artifacts are written to the host's `build/` directory, run the test step on the host runner using the Docker image that now includes Wine:

```yaml
- name: "Run tests (Wine)"
  run: |
    docker run --rm \
      --volume $(pwd):/bemanitools \
      ${{ env.DOCKER_IMAGE }} \
      /bin/sh -c "cd /bemanitools && ./run-tests-wine.sh"
  env:
    DOCKER_IMAGE: "bemanitools-build:latest"
```

Alternatively, if the above docker approach is complex, add Wine directly on the ubuntu-22.04 runner. Per the locked CONTEXT.md decision ("Extend existing Docker build image with Wine"), prefer the Docker approach. If unsure about Docker image name in CI, use the simpler native runner approach:

```yaml
- name: "Run tests (Wine)"
  run: |
    sudo dpkg --add-architecture i386
    sudo apt-get update
    sudo apt-get install -y wine wine32
    ./run-tests-wine.sh
```

Choose whichever approach is cleanest given the existing CI structure. The critical requirement: test failures must produce a non-zero exit code that fails the CI step (red pipeline).

Do NOT change the existing trigger (push to master only). Do NOT modify the build step itself.
