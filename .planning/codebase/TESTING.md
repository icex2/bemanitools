# Testing Patterns

**Analysis Date:** 2026-02-28

## Test Framework

**Custom Assertion Macros:**
- No external test framework (CMake, Catch, gtest, etc.)
- In-house macro-based assertions defined in `src/test/test/check.h` and `src/test/test/check.c`

**Test Execution:**
- Each test compiles to standalone Windows executable
- Manual runner script: `run-tests-wine.sh` (runs via Wine on Linux)
- Invoked via: `make run-tests`

**Build System:**
- GNUmakefile orchestrates compilation
- Module.mk files declare test executables under `testexes` variable
- Location: `Module.mk` lines 143-145 declare test collections
- Tests built for both 32-bit and 64-bit: `build/bin/indep-32/`, `build/bin/indep-64/`

## Test File Organization

**Location:**
- Test files in `src/test/` organized by module they test
- Subdirectory per module: `src/test/cconfig/`, `src/test/security/`, `src/test/util/`
- Each test module has its own `Module.mk`

**Naming:**
- Test file: `{module}-{area}-test.c`
- Examples: `security-id-test.c`, `cconfig-test.c`, `util-net-test.c`
- Corresponds to module being tested: `security-id-test.c` tests `src/main/security/id.c`

**Structure per Test File:**
```
src/test/cconfig/
├── Module.mk               # Declares all testexes for cconfig tests
├── cconfig-test.c         # Tests cconfig_init, cconfig_get, cconfig_set
├── cconfig-cmd-test.c     # Tests cconfig command-line parsing
├── cconfig-util-test.c    # Tests cconfig utility functions
└── iidxhook-util-config-sec-test.c  # Tests security config parsing
```

## Test Structure

**Module-Level Pattern:**

```c
// From src/test/security/security-id-test.c

#include "security/id.h"

#include "test/check.h"
#include "test/test.h"

static void test_to_str()
{
    check_str_eq(
        security_id_to_str(&security_id_default, false),
        "0101020304050607086F");
    check_str_eq(
        security_id_to_str(&security_id_default, true), "0102030405060708");
}

static void test_parse_valid()
{
    struct security_id id;

    check_bool_true(security_id_parse("0101020304050607086F", &id));
    check_bool_true(security_id_verify(&id));
}

TEST_MODULE_BEGIN("security-id")
TEST_MODULE_TEST(test_to_str)
TEST_MODULE_TEST(test_parse_valid)
TEST_MODULE_END()
```

**Key Macros:**
- `TEST_MODULE_BEGIN(name)` - Sets up main() and logging
- `TEST_MODULE_TEST(func)` - Registers a test function to run
- `TEST_MODULE_END()` - Closes main() and returns 0 on success

**Control Flow:**
1. Each test file is compiled as standalone executable
2. Execution starts with `main()` generated by macros
3. Each registered test runs in order
4. Failure in any check calls `abort()` and exits non-zero
5. Success prints "Finished execution of test module"

## Assertion Macros

**Equality Checks:**
- `check_int_eq(expr, expected)` - Verify integer equals expected
- `check_char_eq(expr, expected)` - Verify char equals expected
- `check_float_eq(expr, expected, delta)` - Verify float within delta tolerance
- `check_str_eq(expr, expected)` - Verify string equality
- `check_data_eq(expr, result_size, expected, expected_size)` - Verify binary data

**Inequality Checks:**
- `check_int_neq(expr, expected)` - Verify integer not equal
- `check_char_neq(expr, expected)` - Verify char not equal

**Boolean Checks:**
- `check_bool_true(expr)` - Verify bool is true
- `check_bool_false(expr)` - Verify bool is false

**Pointer Checks:**
- `check_non_null(expr)` - Verify pointer is not NULL
- `check_null(expr)` - Verify pointer is NULL

**Manual Failure:**
- `check_fail()` - Force test failure with no message
- `check_fail_msg(expr)` - Force test failure with message string

**Failure Behavior:**
- On assertion failure: prints file, line, function, expression, actual, expected
- Example output (from check.c implementation):
  ```
  filename.c:42: In test_foo:
      Incorrect result: some_function()
      Return value was 5
      Expected         10
  ```
- Then calls `abort()` to exit process with failure code

## Mocking

**Framework:** No mocking framework; integration tests with real implementations

**Approach:**
- Unit tests link against actual module implementations (see `libs_*` in Module.mk)
- Tests instantiate real structures and call functions directly
- Example: `src/test/security/security-id-test.c` creates `struct security_id` and calls `security_id_parse()` with real parsing logic

**Boundary Mocking:**
- Some modules have stub implementations (like `eamiotest.c` for I/O devices)
- These are alternative implementations in `src/main/` not in `src/test/`
- Location: `src/main/eamiotest/`, `src/main/bio2emu/` provide emulated behavior

**No Mocking Library:**
- Macros or function pointers used for dependency injection where needed
- Example: `eam_io_init()` takes function pointers for thread operations:
  ```c
  bool eam_io_init(
      thread_create_t create, thread_join_t join, thread_destroy_t destroy)
  ```

**What to Mock:**
- Hardware I/O boundaries: use stub modules like `bio2emu` instead of `bio2drv`
- External dependencies: pass as callbacks if module architecture supports it
- Rare in this codebase; most tests use real implementations

**What NOT to Mock:**
- Core data structure operations (parsing, validation, state management)
- Security primitives (they should be tested with real logic)
- Business logic (test the actual algorithm)

## Fixtures and Factories

**Test Data:**
- Hard-coded in test file, not in separate fixture files
- Example from `src/test/security/security-id-test.c`:
  ```c
  check_str_eq(
      security_id_to_str(&security_id_default, false),
      "0101020304050607086F");
  ```
  - `security_id_default` is a module-level constant defined in `security/id.c`

**Initialization Pattern:**
- Each test calls init functions as needed:
  ```c
  static void test_init()
  {
      struct cconfig *config;
      config = cconfig_init();  // Setup

      check_int_eq(config->nentries, 0);  // Verify setup

      cconfig_finit(config);  // Teardown
  }
  ```

**No Factory Classes:**
- Straightforward struct instantiation via init functions
- Init functions return pointer to initialized structure
- Cleanup via finalize functions: `cconfig_finit()`, not `destroy()` or `delete()`

**Location:**
- Fixtures live in test files themselves, not separate directories
- Shared test utilities in `src/test/test/` (the test framework itself)

## Coverage

**Requirements:** Not enforced; no coverage threshold defined

**Explicit Coverage View:** No built-in command

**Manual Assessment:**
- Inspect test files for module being changed
- Check if public API functions have corresponding tests
- Example: `src/test/security/` has tests for:
  - `security_id_to_str()` - tested
  - `security_id_parse()` - tested
  - `security_id_verify()` - tested

**What's Typically Tested:**
- Public API: all functions in module header
- Error conditions: invalid inputs, boundary cases
- State transitions: init → use → fini

**Coverage Gaps (Known):**
- Some hardware-specific code not tested (I/O drivers)
- Configuration parsing has good coverage (cconfig tests)
- Security operations well-tested (security-*-test.c)

## Test Types

**Unit Tests:**
- Scope: Individual module or component
- Approach: Call public function, verify output
- Example: `cconfig-test.c` tests config storage and retrieval
- Dependencies: Real implementations of linked modules (see `libs_*` in Module.mk)

**Integration Tests:**
- Scope: Multiple modules working together
- Approach: Initialize one module that depends on others, verify behavior
- Example: `iidxhook-util-config-*-test.c` tests config parsing which depends on cconfig
- No separate integration test directory; distinction is at test granularity level

**E2E Tests:**
- Not applicable: This codebase is low-level system hooks and I/O drivers
- Real E2E testing happens on actual arcade hardware or via Wine emulation

**Device/Hardware Tests:**
- `src/main/aciotest/`, `src/main/ddriotest/` are executables for manual testing of devices
- Not automated; operator must verify results on hardware
- Different from unit tests: these are interactive

## Common Patterns

**Async Testing:** Not applicable; codebase is synchronous

**Error Testing:**
```c
// From src/test/security/security-id-test.c:23-34
static void test_parse_invalid()
{
    struct security_id id;

    check_bool_true(security_id_parse("0102030405060708", &id));
    check_bool_false(security_id_verify(&id));  // Valid parse, invalid checksum

    check_bool_true(security_id_parse("010102030405060708FF", &id));
    check_bool_false(security_id_verify(&id));  // Valid parse, invalid data

    check_bool_false(security_id_parse("asdf", &id));  // Invalid format
}
```
- Tests both successful parsing with failed verification (state error)
- Tests failed parsing (input error)
- Tests bounds (too long input)

**State Verification:**
```c
// From src/test/cconfig/cconfig-test.c:11-15
check_int_eq(config->nentries, 0);
check_null(config->entries);
```
- Directly access structure fields to verify internal state
- Acceptable pattern in this codebase: structures are opaque to callers but internal to module

## Building and Running Tests

**Build All Tests:**
```bash
make build          # Compiles all tests (among other targets)
make code-format    # Format code before testing
make run-tests      # Runs all test executables via run-tests-wine.sh
```

**Individual Test Binary:**
- Built to: `build/bin/indep-32/{testname}.exe` or `build/bin/indep-64/{testname}.exe`
- Run via Wine: `wine build/bin/indep-32/security-id-test.exe`

**Test Runner Script:**
- Location: `run-tests-wine.sh`
- Invoked via: `make run-tests`
- Runs all `testexes` targets listed in Module.mk via Wine
- Exit status 0 on all passes, non-zero if any fails

**Typical Test Output:**
```
Executing test module 'security-id'...
    Running test 'test_to_str'...
    Running test 'test_parse_valid'...
    Running test 'test_parse_invalid'...
    Running test 'test_prepare_and_verify'...
    Running test 'test_prepare_and_verify_invalid'...
Finished execution of test module
```

## Test Module Declarations

**Example Module.mk** (from `src/test/security/Module.mk`):

```make
testexes            += security-id-test

srcdir_security-id-test := src/test/security

libs_security-id-test     := \
    security \
    test \
    util \

src_security-id-test     := \
    security-id-test.c \
```

**Key Variables:**
- `testexes` - List of test executable names
- `srcdir_{name}` - Source directory for test
- `libs_{name}` - Static libraries to link (from `src/main/*/Module.mk`)
- `src_{name}` - Source files for test

**Library Dependencies:**
- `test` library provides `check.h` macros and implementations
- `security` library provides the code being tested
- `util` library provides logging and utilities
